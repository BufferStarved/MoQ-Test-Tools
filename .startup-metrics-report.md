# Startup breakdown — shipped, deployed, verified

Branch `feat/moq-draft-18`, deployed to `moq.sean-mccarthy.net` (`4dfaadc`).
Regression green: **349 Python tests**, `tsc --noEmit` 0 errors, 33 frontend
unit scripts pass (baseline was 290 tests).

## 1. The phase list as shipped

**Publisher chain** — job start → first media confirmed at the ingest:
`startup_dns_ms`, `startup_connect_ms`, `startup_handshake_ms`,
`startup_publish_accept_ms`, `startup_first_idr_ms`, `startup_first_byte_ingest_ms`

**Player chain** — player attach → first painted frame:
`startup_player_request_ms`, `startup_manifest_ms`, `startup_first_media_ms`,
`startup_first_paint_ms`

**Reconciliation**, per half, both signed:
`startup_publisher_accounted_ms` / `_measured_ms` / `_residual_ms` / `_overcount_ms`,
the same four for `startup_player_*`, plus `startup_unmeasured` and
`startup_not_applicable`. Twenty columns.

### Why two halves and not one total

Between "the ingest has the first byte" and "an operator opened the tile" sits
dwell time belonging to neither pipeline. A joined total would be dominated by
human reaction time. The publisher chain reconciles against job-start →
first-byte-at-ingest; the player chain reconciles against `playback_ttff_ms`.

### Three states, not two

`latency_budget` distinguishes measured from unmeasured. Startup needs a third:
a phase that **structurally does not exist**. SRT has no TCP connect — its
caller handshake *is* the connect. Raw MPEG-TS playback has no manifest.
Calling those "unmeasured" sends an operator hunting for an impossible
instrument, so they report `not_applicable`, and their time is attributed to
the phase that genuinely contains it (SRT's handshake is anchored at
`dns_done`, so the whole exchange lands there).

A missing *middle* milestone unmeasures **both** neighbours rather than
stretching one across the gap. Donating a missing handshake to `publish_accept`
would read as a slow ingest — the exact misattribution this family exists to
prevent. (This was a real bug in my first draft, caught by
`test_missing_middle_milestone_unmeasures_both_neighbours`.)

## 2. Per-protocol mapping, and what is unmeasured

### Publisher half — live status

| phase | RTMP | SRT | WHIP | MoQ |
|---|---|---|---|---|
| `dns` | measured (0.1–0.2 ms) | measured (0.1–0.2 ms) | measured (0.2 ms) | measured (50.8–138.3 ms) |
| `connect` | measured (34.7–39.6 ms) | **n/a** (no TCP connect over UDP) | measured (34.7–39.0 ms) | unmeasured |
| `handshake` | unmeasured | unmeasured | unmeasured | unmeasured |
| `publish_accept` | unmeasured | unmeasured | unmeasured | unmeasured |
| `first_idr` | unmeasured | unmeasured | measured (984–1001 ms) | unmeasured |
| `first_byte_ingest` | unmeasured | unmeasured | unmeasured | unmeasured |

**Why they are unmeasured (honest accounting):**

- `handshake` — RTMP's C0/C1/S0/S1/S2 and SRT's caller handshake happen inside
  ffmpeg, which at default verbosity prints nothing timestamped. Measuring it
  needs `-loglevel verbose` stderr parsing, which was not wired. MoQ's
  WebTransport milestone has a real source (`publisher_webtransport_connected`)
  but is not reaching the tracker.
- `publish_accept` / `first_byte_ingest` — the detectors exist
  (`_ingest_receive_observed`, `publisher_catalog_published`,
  `publisher_first_object_sent`) but are not feeding the tracker on the
  RTMP/SRT/MoQ paths. **This is the main incomplete piece**, not a structural
  limit.
- `first_idr` — works on the WHIP path only; the same ffmpeg `frame>=1`
  progress signal should light it on every protocol.
- MoQ `connect` — means the QUIC handshake, which nothing in the API process
  observes. `startup_probe` deliberately refuses to substitute a TCP connect:
  it would either be refused or succeed against an unrelated listener and chart
  as a transport connect that never happened.

Publisher-side sampling is quantized to the **1 Hz** loop, so its phases carry
~1 s granularity. DNS and connect come from a dedicated preflight and are
genuinely sub-millisecond.

### Player half — live status

Fully working on every engine. `manifest` is **n/a** on raw MPEG-TS (no
manifest exists). `first_paint` is unmeasured on WHEP (no `timeupdate`-based
paint instant on that path yet).

## 4. Laptop-published RTMP → Linode Zixi

Job `0becfbc9-3cb2-4341-968e-59d09a27d442`, `publisher_host=local`
(agent-7145 / Seans-MBP), mpegts player.

| | TTFF |
|---|---|
| laptop baseline (docs/RTMP-STARTUP.md) | ~23000 ms |
| **laptop, now** | **1721 ms** |
| cloud-encoded | 1501 ms |

The 23 s → 1.5 s win is **not** an artifact of moving to cloud encode. The same
laptop publisher joins ~13.4× faster than its own baseline and lands within
220 ms of the cloud number — small enough to be uplink RTT rather than
pipeline. e2e 1295 ms, 48 frames painted.

Caveat: the leg later reported an ffmpeg I/O error because an orphaned earlier
job of mine still held the Zixi `benchmark` push input. TTFF was measured
before that and stands, but the leg deserves a clean re-run.

### What actually blocked this, precisely

Not what was reported. Two independent gates, and a bug:

1. `web/api/main.py:705` rejects any `media_path` ending `dummy.mp4` **by
   filename** when `publisher_host=local` ("VOD presets are for cloud encode
   only"). The repo's standard fixture can never be used.
2. `main.py:721` then requires `os.path.exists` **on the API host** while the
   agent opens the same absolute path **on the laptop**. The roots differ
   (`/Users/sean/Developer/moq-test-tools` vs `/opt/moq-test-tools`), so no
   repo-relative path satisfies both.
3. `scripts/qa_local_ttff.py` read `job["job_id"]`, but the job record's field
   is `id`. It raised a KeyError **after successfully starting the job**, which
   is why this looked like an API rejection when the encoder was already
   running. Fixed in `27a43c9`.

Workaround: an absolute path present on both hosts with a non-VOD filename
(`/tmp/laptop-rtmp-qa.mp4`). The durable fix, not done here, is for the API to
skip the local-host existence check when `publisher_host=local` — it is
validating a path it does not own.

## 5. What surprised me

**`first_paint` dominates the HLS/MPEG-TS join, and it is not close.** I
expected `first_media` (fetching the first segment across the network) to be
the cost. Instead, on every mpegts leg the time from *first media byte
received* to *first painted frame* is the largest single phase:
1924.5 ms of a 2502 ms SRT join (77%), 1156.8 ms of 1553 ms on RTMP east.
The bytes arrive quickly; the player then sits on them. That is mpegts.js
buffering before it will start playback — a client-side policy, not transport.

The contrast with MoQ makes it unambiguous: MoQ's `first_paint` is **63–71 ms**
across all three providers, roughly 25× faster, while its `first_media` is
comparable (217–710 ms). Same network, same encoder, same file. The entire
HLS/TS startup penalty is the player's buffering decision, and it is now a
column instead of a hypothesis.

Second surprise: MoQ's `dns` is 50–138 ms against 0.1–0.2 ms everywhere else —
the relay hostnames are not in the resolver cache the way the Zixi/MediaMTX
hosts are. Small in absolute terms, but it is 10% of MoQ west's entire 774 ms
join.

## 6. Not finished, and remaining risk

- **The publisher half is thin.** `handshake`, `publish_accept` and
  `first_byte_ingest` are unmeasured on all four protocols, and `first_idr`
  only lights on WHIP. The detectors already exist in `upload_service.py`;
  they are not wired into the tracker. Until they are, the publisher chain
  only reconciles on WHIP. This is the single biggest gap.
- **Three Linode legs predate the reconciliation fix** and show blank
  `accounted`. Re-running them is a 3-minute job.
- **SRT on GCP west failed** with a 404 from the Zixi origin (rendered 0). That
  is an ingest-side problem, not a metrics one, but it means west SRT is
  unverified.
- **WebRTC on GCP west was never run** (soak-test contention, by instruction).
- **WHEP `first_paint` is unmeasured**, so WHEP carries a small permanent
  residual.
- **Cross-origin Resource Timing opacity** is handled (returns null, never 0)
  but the mpegts/HLS `manifest` phase is reported n/a rather than measured, so
  Resource Timing's DNS/connect/TLS sub-marks are not yet contributing on those
  engines as much as they could.

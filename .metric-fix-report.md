## Per-defect before -> after

**D1 residual clamp / over- vs under-attribution — FIXED.**
WebRTC before: 23 samples over-attributed, max **1721.2 ms**, and
`latency_overcount_ms` was *never emitted* — the clamp swallowed it. After:
over-attribution is reported, `latency_overcount_ms` nonzero 5/30, max
**14.9 ms**, and the audit's `silent_over` count is 0. The 100x collapse is the
scope fix: `latency_e2e_scope=ingest_to_glass` now keeps the 1406.5 ms
sender-side encode out of a receiver-side WHEP e2e of ~16 ms. Summing it in was
almost the entire 1721.2 ms.

**D2 frame_delivery_pct windowing — PARTIAL, still fails.**
RTMP 48.0 -> 10.06 became **100.0 -> 40.0**; WebRTC 36.76 -> 8.03 became
**101.61 -> 40.13**. Two real wins: the ratio now *starts* at a correct 100
instead of a diluted 48, and the peak above 100 confirms the 100% cap is gone
(`_DELIVERY_MAX_PCT = 1000.0`). It also blanks instead of running to the end of
the leg. But the decay is not gone, and the RTMP per-sample trace shows exactly
why:

```
 i  enc_frames  rendered  delivery  age
  7        175        73    100.00    0
  8        205        73     66.67    1
  9        235        73     50.00    2
 10        265        73     40.00    3
 11        295        73   (blank)    4
```

The player freezes at 73 rendered. `frame_delivery_pct` is still **recomputed**
during the 3 s staleness grace window using a *fresh* encoder counter against a
*stale* player counter, so it decays 100 -> 66.67 -> 50 -> 40 before blanking.
The fix should hold the encoder counter at the player's last report (or blank as
soon as `playback_sample_age_sec > 0`) rather than only blanking past 3 s. The
damage is now bounded to 3 samples instead of the whole run, but the audit
invariant (peak-to-last drop > 20) still trips.

**D3 publish stage — FIXED.** All four legs, before: `latency_publish_ms` 0 on
every sample with nothing declared. After: still 0, but `publish` appears in
`latency_unmeasured` on 100% of samples in all four legs, and
`reported_while_unmeasured` is 0 everywhere.

**D4 packager on Zixi — FIXED.** `packager` declared 30/30 on both RTMP and SRT.

**D5 `_clean_ms` ceiling — indirect evidence only.** No leg produced an
over-ceiling component, so the `min()`-vs-0.0 change was not exercised
directly. The MoQ e2e of 23050 ms does survive intact under the new
`_E2E_MAX_MS = 180_000`, where the old 60 s component ceiling would have applied.

**D6 MoQ LOC behind-live — DID NOT HOLD.** This is the one regression to flag.

* Run 1: 10924.7 ms -> **0.0** on all 22 samples, `player_buffer` declared
  unmeasured 22/22. Fix appears to work.
* Run 2, same preset and same player: `latency_player_buffer_ms` =
  **8059.6 ms**, exactly `playback_buffer_sec` (8.059586) x 1000, and
  `player_buffer` declared unmeasured on only 17/23.

The backend contract in `src/latency_budget.py` is right — it declares
`player_buffer` unmeasured only when `playback_buffer_sec is None`. What differs
between the runs is sample freshness, not the LOC split: run 1's
`playback_sample_age_sec` is empty for those rows and run 2's is 0. So run 1 was
protected *incidentally* by staleness blanking, and as soon as a MoQ playback
sample is fresh, a behind-live-sized figure lands back in the buffer stage.

Compounding it: `playback_behind_live_sec` exists in `web/api/main.py` and
`MoqPlayer.tsx` but is **not in the archived CSV header**, so the archive cannot
distinguish "8 s genuinely queued ahead" from "8 s behind live". Add the column
before re-testing D6.

**D7 forward-fill — FIXED.** Trailing verbatim e2e repeats:

| leg | before | after |
|---|---|---|
| RTMP | 5522.0 x 23/30 | 5677.0 x **4**/30 |
| WebRTC | 35.0 x 22/30 | 16.0 x **4**/30 |
| SRT | 8167.0 x 19/30 | 8167.0 x **4**/30 |

`playback_sample_age_sec` climbs 0..22 and the column blanks past age 3. The
remaining 4 repeats are the intended 3 s grace window, under the audit's
threshold of 5.

**D8a MoQ net_rtt — FIXED.** `latency_network_ms` 0 on all 23 and undeclared
before; now declared `network` 22/22 (run 1) and 23/23 (run 2).

**D8b headline fps — still fails 3 legs, but the audit check is wrong.**
Confirms the earlier "AUDIT DIAGNOSIS WAS WRONG" note, now with numbers. The
audit divides frames produced between the first and last *nonzero*
`encode_frames_total` by the *full* sample wall-clock — including the leading
samples where the encoder had not started. Recomputing over the matching
interval:

| leg (after) | audit counter | corrected counter | rate mean | audit gap | true gap |
|---|---|---|---|---|---|
| RTMP | 27.933 | **30.003** | 30.801 | 2.868 | **0.798** |
| WebRTC | 28.236 | **31.485** | 31.397 | 3.161 | **0.088** |
| SRT | 29.025 | **30.036** | 29.989 | 0.965 | **0.046** |
| MoQ | 30.615 | 30.615 | 32.637 | 2.022 | **2.022** |

RTMP's encoder produced 810 frames between t=2.0 s and t=29.0 s — exactly
30.0 fps. The audit divides by 29.0 s instead of 27.0 s and reports 27.93. With
the denominator fixed, RTMP, WebRTC and SRT all clear the 1.5 threshold.

MoQ is the exception and its gap is **real**: the correction changes nothing
(its frame counter is nonzero on every sample), so 32.637 vs 30.615 stands. That
is startup oscillation, not a broken formula — `fps_stability` is 0.19 on MoQ
versus 0.0006 on SRT, and `speed` peaks at 1.92 as the file source races ahead.
The audit's own `fps_truth` docstring says a large gap means oscillation rather
than a broken number; `check_invariants` then fails the leg for it anyway. The
invariant contradicts its own documentation and should be rewritten (fix the
denominator, and gate on `fps_stability` instead of the raw gap).

## What did not improve, or got worse

1. **D6 regressed between two identical MoQ runs** (0.0 ms vs 8059.6 ms). Not
   fixed; see above.
2. **D2 still decays** on RTMP and WebRTC, now bounded to the 3 s grace window.
3. **Residual percentages went up, not down** — MoQ 54.9% -> 95.5%, RTMP 84.9%
   -> 85.4%, SRT 96.1% -> 95.9%. This is the fix working, not a regression: the
   model stopped *claiming* stages it never measured. On MoQ only
   `latency_encode_ms` (1040 ms) is instrumented against a 23 s e2e, so 95.5% is
   the honest number, and the row now names all four blind stages. D1 was about
   the clamp hiding attribution errors, not about shrinking the residual.
4. **`frame_delivery_pct` on MoQ went from wrong to absent** — 5/23 nonzero
   (peak 8.52) before, 0/22 after, because D2 returns `None` without a shared
   window. Honest, but the metric no longer exists on that protocol.
5. **`playback_behind_live_sec` is not archived to CSV**, so D6's replacement
   signal is invisible to the audit.
6. MoQ run 1's job ended `failed` (`moq5 publisher exited with code 1 ...
   write(vide_1) failed: -4`) after the player detached. Run 2 passed, so this
   is intermittent and unrelated to the metric work.

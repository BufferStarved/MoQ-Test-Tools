## Per-defect before -> after

**D1 residual clamp / over- vs under-attribution — FIXED.**
WebRTC before: 23 samples over-attributed, max **1721.2 ms**, and
`latency_overcount_ms` was *never emitted* — the clamp swallowed it. After:
over-attribution is reported, `latency_overcount_ms` nonzero 5/30, max
**14.9 ms**, and the audit's `silent_over` count is 0. The 100x collapse is the
scope fix: `latency_e2e_scope=ingest_to_glass` now keeps the 1406.5 ms
sender-side encode out of a receiver-side WHEP e2e of ~16 ms. Summing it in was
almost the entire 1721.2 ms.

**D2 frame_delivery_pct windowing — PARTIAL, still fails.**
RTMP 48.0 -> 10.06 became **100.0 -> 40.0**; WebRTC 36.76 -> 8.03 became
**101.61 -> 40.13**. Two real wins: the ratio now *starts* at a correct 100
instead of a diluted 48, and the peak above 100 confirms the 100% cap is gone
(`_DELIVERY_MAX_PCT = 1000.0`). It also blanks instead of running to the end of
the leg. But the decay is not gone, and the RTMP per-sample trace shows exactly
why:

```
 i  enc_frames  rendered  delivery  age
  7        175        73    100.00    0
  8        205        73     66.67    1
  9        235        73     50.00    2
 10        265        73     40.00    3
 11        295        73   (blank)    4
```

The player freezes at 73 rendered. `frame_delivery_pct` is still **recomputed**
during the 3 s staleness grace window using a *fresh* encoder counter against a
*stale* player counter, so it decays 100 -> 66.67 -> 50 -> 40 before blanking.
The fix should hold the encoder counter at the player's last report (or blank as
soon as `playback_sample_age_sec > 0`) rather than only blanking past 3 s. The
damage is now bounded to 3 samples instead of the whole run, but the audit
invariant (peak-to-last drop > 20) still trips.

**D3 publish stage — FIXED.** All four legs, before: `latency_publish_ms` 0 on
every sample with nothing declared. After: still 0, but `publish` appears in
`latency_unmeasured` on 100% of samples in all four legs, and
`reported_while_unmeasured` is 0 everywhere.

**D4 packager on Zixi — FIXED.** `packager` declared 30/30 on both RTMP and SRT.

**D5 `_clean_ms` ceiling — indirect evidence only.** No leg produced an
over-ceiling component, so the `min()`-vs-0.0 change was not exercised
directly. The MoQ e2e of 23050 ms does survive intact under the new
`_E2E_MAX_MS = 180_000`, where the old 60 s component ceiling would have applied.

**D6 MoQ LOC behind-live — DID NOT HOLD.** This is the one regression to flag.

* Run 1: 10924.7 ms -> **0.0** on all 22 samples, `player_buffer` declared
  unmeasured 22/22. Fix appears to work.
* Run 2, same preset and same player: `latency_player_buffer_ms` =
  **8059.6 ms**, exactly `playback_buffer_sec` (8.059586) x 1000, and
  `player_buffer` declared unmeasured on only 17/23.

The backend contract in `src/latency_budget.py` is right — it declares
`player_buffer` unmeasured only when `playback_buffer_sec is None`. What differs
between the runs is sample freshness, not the LOC split: run 1's
`playback_sample_age_sec` is empty for those rows and run 2's is 0. So run 1 was
protected *incidentally* by staleness blanking, and as soon as a MoQ playback
sample is fresh, a behind-live-sized figure lands back in the buffer stage.

Compounding it: `playback_behind_live_sec` exists in `web/api/main.py` and
`MoqPlayer.tsx` but is **not in the archived CSV header**, so the archive cannot
distinguish "8 s genuinely queued ahead" from "8 s behind live". Add the column
before re-testing D6.

| WebRTC | 35.0 x 22/30 | 16.0 x **4**/30 |

`playback_sample_age_sec` climbs 0..22 and the column blanks past age 3. The

**D8a MoQ net_rtt — FIXED.** `latency_network_ms` 0 on all 23 and undeclared
before; now declared `network` 22/22 (run 1) and 23/23 (run 2).

**D8b headline fps — the audit was wrong; only MoQ ever had a real gap. FIXED
in the audit.**

The audit took the numerator from the samples that carry a frame count and the
denominator from *every* sample, so the leading samples recorded before the
encoder produced its first frame padded the divisor without adding to the
dividend. RTMP's encoder produced 810 frames between t=2.0 s and t=29.0 s —
exactly **30.003 fps** over its 26.997 s active window. The audit divided 810 by
28.998 s, reported 27.933, and billed the 2.07 fps it had invented to the
encoder.

`fps_truth` now pairs timestamp and counter row-aligned and divides by the
active window (`scripts/qa_metric_audit.py`). Both counters below are the
audit's, before and after that one change; the rate mean and the CSVs are
untouched:

| leg (after) | audit counter | corrected counter | rate mean | audit gap | true gap |
|---|---|---|---|---|---|
| RTMP | 27.933 | **30.003** | 30.801 | 2.868 | **0.798** pass |
| WebRTC | 28.236 | **31.485** | 31.397 | 3.161 | **0.088** pass |
| SRT | 29.025 | **30.036** | 29.989 | 0.965 | **0.047** pass |
| MoQ run 1 | 30.615 | 30.615 | 32.637 | 2.022 | **2.022** fail |
| MoQ run 2 | 29.807 | 29.807 | 31.734 | 1.927 | **1.927** fail |

The three D8b failures on RTMP, WebRTC and SRT were therefore an **audit
artifact — there is no product defect there to investigate.** The per-sample
`fps` column and the encoders were always right. The same correction applied to
the pre-fix baseline CSVs drops RTMP's gap to 0.129 and WebRTC's to 0.194, so
two of the 19 baseline findings were artifacts too, which is why the honest
baseline is 17.

MoQ is the genuine exception and the correction changes nothing for it: its
frame counter is nonzero on every sample, so its window already *was* the whole
run and 32.637 vs 30.615 stands. That is startup oscillation, not a broken
formula — `fps_stability` (a coefficient of variation) is **0.190** on MoQ
against **0.0003** on SRT, and `speed` peaks at 1.92 as the file source races
ahead of realtime.

So the check now gates on `fps_stability` rather than on the gap alone, because
a gap by itself does not say which number is wrong. Above `FPS_UNSTEADY_CV`
(0.05, an order of magnitude clear of both the 0.19 and the 0.0003 cluster) the
finding reads *unstable encode* and says both numbers are honest; below it the
finding reads *fps formula defect*, because a steady encoder cannot produce two
fps figures 1.5 apart. MoQ still fails — deliberately — with:

```
! unstable encode: rate-mean 32.637 vs counter-derived 30.615 (796 frames over a
  26.0s active window), gap 2.022; fps_stability 0.1904 >= 0.05 means the encoder
  throughput genuinely oscillates, so both numbers are honest — a product
  observation, not a metric formula defect
```

This also removes the contradiction where `fps_truth`'s docstring said a large
gap meant oscillation and `check_invariants` then failed the leg as if it meant a
broken number.

## Audit sanity check (session 5)

Having found one bad denominator, the rest of `qa_metric_audit.py` was read for
the same mistake and for the more dangerous inverse. **A false failure costs an
investigation; a false pass ships a broken metric.** Ranked by that.

### The same denominator bug is still live in the product

`MetricsCollector._compute_averages` in `src/metrics.py` — the block that
overrides `averages["fps"]`, reached from `write_summary`; line numbers are
drifting under concurrent edits, so grep for it — computes the archived headline
fps exactly the way the audit did: `frames` filtered to nonzero, `stamps` not,
`max - min` over both. So the summary JSON understates fps for any leg whose
encoder had not started at sample 0:

| leg | `averages.fps` in the archived summary | true |
|---|---|---|
| RTMP `upload_20260823-014026_f37981b8` | **27.933** | 30.003 |
| SRT `upload_20260823-014058_6d21f471` | **29.025** | 30.036 |

That 27.933 is bit-identical to the audit's old wrong counter, which is the proof
they share the arithmetic. So the D8b finding was pointing at a real number that
really is wrong — it just named the wrong owner: the per-sample `fps` column and
the encoder are fine, and the defect is in the summary. Not fixed here: another
agent holds `src/**` this session. Its `frames` filter is also a *string*
compare (`not in ("", "0")`), so a `"0.00"`-formatted zero would not be filtered
at all.

### False passes in the audit — every invariant is "data present and wrong"

None of the checks assert that a leg produced the data being judged, so absence
reads as compliance. Concretely, on the legs just scored:

1. **D2 passes on MoQ by having no metric at all.** `frame_delivery_pct` is
   0/22 nonzero after the fix, so the decay check has nothing to compare and the
   leg passes. Item 4 of "what got worse" is therefore also a hole in the gate.
2. **The MoQ `latency_player_buffer_ms` check passed run 1 only because the
   values were blanked.** `series()` drops blanks before `max() > 3000`, which is
   why run 1 read 0.0 and run 2 read 8059.6 from the same preset. The report
   already called that "protected incidentally"; it is the audit, not the fix.
3. **A component that is *never emitted* is not a silent zero.** The silent-zero
   loop runs `if values and not any(v > 0 ...)`, and `series()` returns `[]` for
   an all-blank column, so a column that never appears is skipped. The tables
   print `<- never emitted` and the leg still passes.
4. **Partial unmeasured declarations satisfy the check.** `unm["stages"].get()`
   returns a string like `"17/23"`, which is truthy, so a component reading 0 on
   all 23 samples while declaring itself unmeasured on only 17 passes. That is
   exactly the MoQ run-2 shape, so it is not hypothetical.
5. **`reconcile()` skips every row with `e2e <= 0`** and nothing asserts
   `samples_with_e2e > 0`. A leg whose e2e collection died entirely passes D1,
   D5 and D7 and can be reported clean.
6. **D8b skips itself when `counter_fps` is `None`** — no frame counter, no
   check.
7. **`PLAUSIBLE` is printed, never asserted.** `summarize_column` counts
   implausible values per column and `check_invariants` never reads the count, so
   an fps of 500 or a 0.02 ms RTT prints a marker and passes.
8. **`HONEST_ZEROS` is dead config.** Defined and documented as if it gated
   something; never referenced. The transport columns (`moqx_*`, `quic_*`,
   `cmaf_*`, `pkt_*`) are neither excused nor checked anywhere.
9. **`num()` returns `None` on unparseable input**, which by items 1-6 means a
   malformed cell is indistinguishable from a pass.

### Fixed in passing

- **`frame_trend`'s `player_frozen_after_sample` had the identical windowing
  bug** — an index into the blank-filtered list, quoted as a sample number — and
  reported `None` ("never froze") for a player counter that never advanced at
  all, the worst case. Now row-aligned. Diagnostic only; no verdict moved.
- Dead `over_rows` binding removed; `HONEST_ZEROS` and the absence-of-signal
  limits documented at the top of the file so a clean verdict is not over-read.
- `load_rows()` now accepts a local path, so a change to a formula in the audit
  can be proved against an archived leg without a live server.

### One false failure the fix does not introduce

Narrowing the window cannot hide a slow encoder: D8b asks whether the two fps
columns agree, not whether the encoder hit 30 fps, and a genuine underrun moves
both equally. The one new blind spot is a counter that *resets* mid-leg
(`produced <= 0`), which yields no `counter_fps`; `frames_produced` is now
printed unconditionally so that case is visible rather than silent.
